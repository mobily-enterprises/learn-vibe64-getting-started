# Orientation observation contract (version 1)

Formative evidence, not anti-cheating proof. The app supplies no learner identity, assessment result or durable progress. The host authenticates the person and binds its active pinned attempt/project/session, exact Preview window and initiating browser client. Colleague cannot send observations through its tools.

The app announces `{type:"orientation-available", protocolVersion:1, instanceId:<server UUID>}` after reading its actual server identity. The host checks `event.source` against the expected Preview iframe; this announcement is readiness only. It transfers one MessagePort to that exact frame in `{type:"orientation-init", protocolVersion:1, playerInstanceId:<fresh host UUID>}`. For an opaque frame `*` may be necessary; the expected window, instance and transferred channel establish binding, not an origin string alone.

The app accepts one channel from its immediate parent. Every outbound port message includes `protocolVersion`, `playerInstanceId`, `instanceId`, and `type`. `ready` adds nothing. A trusted button gesture sends `button` with fresh UUID `interactionId`, then `request` with that ID, `method:"POST"`, `path:"/api/greeting"`. After the real response reaches the output and an animation-frame callback runs, `response-displayed` includes the interaction ID, server UUID `requestId`, and `message:"Hello from the server!"`. Scripted clicks run the app but emit no learner observation. Fields contain no HTML, source paths, secrets, actor or claimed pass. The callback is fenced by the exact request ID, render revision and displayed request-reference text, so an older identical greeting cannot emit a stale display observation. An animation-frame callback and document visibility are not proof that Preview is foreground; the host separately validates actual Preview visibility. Host validates exact bounded shapes, rejects stale instances and correlates all three phases. A teacher demonstration keeps demonstration origin even if its browser gesture is trusted.

The existing managed finite-execution owner invokes `node <pinned training/checks/orientation-app/response.mjs>` with one JSON document on stdin followed by EOF:

```json
{"origin":"http://127.0.0.1:8080","instanceId":"<server UUID>","interactionId":"<gesture UUID>","requestId":"<response UUID>"}
```

Origin is resolved from the prepared service's execution metadata, never arbitrary browser/model input. The check accepts only HTTP loopback with an explicit port. Input limit is 4096 characters/five seconds; request timeout is three seconds. Host also applies its normal finite-command timeout/output limits. One JSON row returns `check:"orientation-response"`, `outcome:"verified"`, exact identities/message and exit 0, or `outcome:"incomplete"`, bounded reason and exit 1. Verified means the actual server recorded this response; host still requires the matching response-display observation and learner-origin native context before recording a step pass.

At most 64 records are stored in memory. Restart or eviction expires evidence. If a response identifies a different server instance, the page closes its old channel, disables the request button and explicitly asks for **Reload preview**. Reload obtains the new instance and requires a new host channel, then a fresh button press. If the instance is unchanged but an observation was evicted, a fresh press is sufficient. Never reconstruct old evidence. Standalone execution works without a parent/channel and implies no training progress. No second Preview/process owner or telemetry service is introduced.

The browser uses ordinary same-origin fetch credentials so native Preview authorization continues working. It never reads cookies/tokens, includes them in observations, or gives them to the diagram. The existing proxy remains responsible for authorizing and stripping its own preview cookie before the request reaches this application.
