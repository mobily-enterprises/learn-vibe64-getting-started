## Explain the choices first

“Z.AI supplies the model; Vibe64 is where we'll use it. An API key lets Vibe64 access your Z.AI account. Treat it like a password.” Never request the key in chat, even a few characters. Never put it in lesson answers, screenshots, source files or project settings.

The requested **GLM-4.7** uses paid regular-API credit. **GLM-4.7-Flash** is a different model, currently listed as free. Registration and creating a key do not themselves grant paid-model access. Check [Z.AI's current pricing](https://docs.z.ai/guides/overview/pricing) before choosing paid use; these facts were checked on 8 October 2026. Do not promise that full GLM-4.7 is free or that Flash is the same model. If the learner prefers the free option, explain it and wait for an explicit choice rather than silently substituting it.

This lesson uses the **regular Z.AI API through OpenCode**. A **Personal Coding Plan** is a separate subscription route with different access and quota. Do not redirect a regular-key learner into the Coding Plan setup or claim that its quota covers the regular API. The person decides about payment, purchases, provider consent and paid-model access.

## Open the normal account controls

Guide the learner to **AI Accounts** in Management. Colleague can open that page through its supported navigation action when requested; opening a page changes no settings. A hosted workspace owner can manage AI connections. If the learner is a member without that permission, explain the restriction and ask them to involve the owner; do not try another account or bypass the control.

Choose **Connect regular Z.AI API** when that shortcut is visible. An existing Coding Plan connection can hide it even when the regular API is not connected. In that case, choose **Add connection**, then **Choose provider** on the **OpenCode** card. Wait for the actual catalogue, search **Search OpenCode providers** for “Z.AI”, and choose the regular **Z.AI** row (`zai`), not **Z.AI Coding Plan**. The key editor heading is **Connect regular Z.AI API**.

The starter/onboarding setup offers **Create a regular Z.AI API key**. The generic provider editor does not have that button; use the same [Z.AI API key-management page](https://z.ai/manage-apikey/apikey-list) instead. Both paths lead to human registration and key creation outside Vibe64. On a phone the setup dialog can fill the screen; scroll it to the same controls. Keep the Learning conversation saved while you use the account controls. If Colleague is open, minimise its drawer when you need the space; its avatar launcher restores that separate helper. Return to Learning to continue this lesson. Use the actual controls offered by the host on this device.

## Register and create the key — the person does this

Follow [Z.AI's official getting-started instructions](https://docs.z.ai/guides/overview/quick-start): register or sign in, open API key management and create a key. Complete the provider's actual verification and consent steps. If a paid model needs credit, inspect Billing yourself; creating a key does not require agreeing to a purchase in this lesson.

Suggested invitation: “Open Z.AI's key page using the setup button or the link above. Finish Z.AI's sign-in steps and create your key there. Keep it private; we'll paste it into Vibe64's API key field, not this chat.” Wait while the person uses the external site. Do not ask them to read out a code or secret, open a shell, or send a screenshot of the key. Colleague has no source, shell or screenshot access for these steps.

Return to Vibe64's setup dialog. Paste the key into the masked **API key** field. Press **Verify and connect**; on the initial onboarding surface the label is **Verify key and start Vibe64**. The existing verifier makes a tiny GLM-4.7 Flash request on the regular API before saving. This checks that route/key; it does not prove entitlement to full GLM-4.7.

Wait for the saved connection state. A failed or interrupted check is not success. Keep the working dialog and read its actual error; retry its supported verification when appropriate, without posting the key here. A connection can be saved even if its later routing setup failed: explain that distinction and finish routing instead of saying the working key was rejected.

Offer the distinct Flash option without choosing it for them.

## Choose the future OpenCode Senior default

“Main is the coding conversation, and Main Learning teaches this lesson. Colleague is the assistant helping you use Vibe64. Their model choices are separate.” Connecting a key is not the same as choosing which model a conversation will use.

In **AI Accounts**, open OpenCode's **Configure routing**. For future OpenCode Senior coding conversations, choose the exact offered **GLM-4.7** model for **Senior**, review the selection and press **Save routing**. The post-connect screen may instead show **Current** and **Suggested** choices with **Apply [number] changes**. Review every proposed change; **Keep current routing** leaves the connection ready without applying those suggestions.

Only save the changes the person requested. Colleague can read the current revision, preview supported routing changes and save them when the owner explicitly authorises it. It cannot connect the key or consent to paid access. Do not replace unrelated Helper, Router or Shared backup choices. **Junior** is the everyday model used by Junior or some Auto requests and by new Learning teachers. Changing Senior alone does not change Junior. Preview a separate Junior routing change only if the person also requests it, explaining that it also affects ordinary Junior coding work. Do not claim all Main or Learning chats use GLM-4.7 after a Senior-only change.

A saved **Custom** choice in an existing Main conversation stays separate. Its mode menu offers **Custom**, then **Orchestrator**, **Model**, **Thinking** and **Apply** for that conversation; **Senior** follows its configured Senior route. Shared routing affects future work, not a running turn. Do not tell a learner to interrupt work just to finish this lesson.

Colleague's own composer model picker changes Colleague's selection, not Main routing. Change it only if separately requested and supported while its work is stopped. The avatar/voice cog does not select the AI model. Avoid offering multiple simultaneous changes to a beginner.

Freshly read the saved routing and actual permitted model before saying the requested future OpenCode Senior default is ready. Name the actual model and scope, such as “future OpenCode Senior chats use GLM-4.7”. If a save is uncertain, reread the current revision and review retained choices; do not blindly repeat or overwrite them. A fresh native model response can prove execution only for the actual conversation/model that produced it, not for every role or provider route.

## Safe AI setup — one short answer

Ask: “Where should your Z.AI key go, which model are we choosing for future OpenCode Senior coding chats, and does that also change Colleague?” Invite one compact answer in the learner's own words; never include the key itself.

Pass on all three useful distinctions: the key goes into Vibe64's masked **API key** field in **AI Accounts**, never chat; the requested future OpenCode Senior model is **GLM-4.7** when paid access is available, distinct from free **GLM-4.7-Flash**; and Colleague's own model is selected separately. Accept ordinary wording such as “I'll put the key in AI Accounts, choose paid GLM-4.7 for future OpenCode Senior coding chats when I can use it, and choose Colleague separately.” If the learner explicitly chose Flash instead, accept an accurate answer naming that free model and the same safety/scope distinctions. Do not pretend this was the requested full-model setup.

Incomplete answers include pasting or reading a secret into chat, claiming registration unlocks every model, treating Flash and full 4.7 as interchangeable, or claiming Senior routing also changes Junior, the current Custom teacher or Colleague. Explain only the missing distinction. A safe but partial answer needs a short follow-up, not a new lecture. If meaning is split across replies, invite a fresh complete independent answer so the original grading owner receives one admitted message for this question. After substantial help, prepare a fresh variation and record that assistance; do not grade a teacher-authored answer as independent.

Use the original prepared-question and accepted-answer assessment flow. Retain the exact question, answer and rubric identities on uncertain retries. Grade only the learner's actual admitted answer, not an unsent draft or recognition partial. The quiz assesses understanding; it cannot manufacture account verification, successful routing, paid access or native execution evidence. Do not record a new account practical assessment or substitute an application/diagram event.
